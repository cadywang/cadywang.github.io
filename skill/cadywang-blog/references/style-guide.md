# 文风与结构指南（cadywang.github.io）

## 读者与语气

- 读者：会写代码的工程师，时间有限，想知道"怎么做、为什么这样做、坑在哪"。
- 语气：第一人称、平实、承认局限（"实测 1~1.2 KB/s，慢是故意的"比"性能卓越"有用得多）。
- 不用营销腔（赋能/极致/一键起飞），不写"本文必将带你"。

## 开头怎么写

3~5 句交代场景与动机，直接点出痛点，最后一句说明本文讲什么：

> 嵌入式调试里有个很常见的尴尬：板子在你手上，但串口线插在另一台机器上。
> 于是写了 serial-debug-bridge：把远端串口变成一个可以用命令行调用的接口。
> 这篇文章分两部分：架构与设计取舍，以及部署与使用指南。

## 章节骨架

可按内容裁剪，但**保留"取舍"和"实测"两节**——这是本站文章最有价值的部分。

1. `## 一、它解决什么问题` —— 角色表 / 背景 / **约束**（约束比目标重要）
2. `## 二、架构` —— 组件图（ASCII）+ 为什么这样拆，而不是做成单进程
3. `## 三、关键设计与取舍` —— 每个决策都写"为什么不选另一种做法"
4. `## 四、实测数据` —— 表格：项目 / 结果；写明环境（版本、机器、参数）
5. `## 五、部署指南` —— 环境要求表 + 分平台步骤
6. `## 六、使用指南` —— 命令表（含退出码）+ 可直接复制的示例
7. `## 七、排障速查` —— 现象 → 原因 → 处理
8. `## 八、小结`（可选）—— 三条主线 + 仓库链接

## 版式习惯

- 大节之间用 `---` 分隔。
- 对比信息一律用表格：读者能直接抄结论。
- 架构/流程用 ASCII 图画在代码块里（不依赖 mermaid，任何渲染器都不会坏）。
- 代码块标语言（bash / powershell / sh / markdown / json）。
- 中文引号用 `「」`；强调用 `**粗体**`；符号只用 ✅ ❌ ⚠️ ★ 这类，不做装饰。
- 命令示例给可直接复制的完整行，别用 `…` 省掉关键参数。
- 篇幅参考 1500~3000 字（约 200~400 行），宁短勿水。

## front-matter 规范

```markdown
---
title: 主标题：副标题（范围）
date: 2026-10-15 14:05:00
tags: [串口, 嵌入式, 远程调试, Python]
categories: [教程]
---
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `title` | 是 | 中文标题，带副标题更清楚 |
| `date` | 是 | `YYYY-MM-DD HH:mm:ss`；**写未来时间 Hexo 会跳过不生成** |
| `tags` | 是 | 3~5 个，中文词 + 技术名词混用，与既有文章保持一致 |
| `categories` | 建议 | 一个；既有文章用 `[教程]`，技术笔记可用 `[技术]` |
| `description` | 可选 | 首页摘要 |
| `draft: true` | 可选 | 草稿，不会被生成；要发布时删掉 |
| `sticky: 1` | 可选 | 置顶 |
| `comments: false` | 可选 | 关闭该篇评论 |

## 反面清单

- 数字没有来源（"快了 10 倍"却不说环境与测法）。
- 整段粘贴代码，却不解释这个文件在链路里干什么。
- 只写"怎么做"、不写"为什么不那样做"——读者遇到变体还是不会。
- 标题党、营销词，正文里夹着 TODO / 待补充。
- 泄露凭据、token、真实内网敏感信息（用示例地址即可）。
